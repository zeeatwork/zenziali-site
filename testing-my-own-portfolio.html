Testing My Own Portfolio

My portfolio's README has a short checklist called Before each publish. Every link goes somewhere real. Check desktop and phone widths. Tab through each page. One H1 per page. No email address. No em dashes.

It's a good list. But for a QA engineer's own site, the only thing between a visitor and a broken page was me remembering to read it.

The first run

The first time the automated checks ran, most of the site passed. One page didn't: my case study, Quality Is Glue Work.

The accessibility scan flagged a traceability table as a serious issue. On a phone, the table is wider than the screen, so it scrolls sideways. A mouse or a finger can do that. A keyboard can't, because nothing in the table could take focus. Someone navigating by keyboard would see half a table and have no way to reach the rest.

The page had been reviewed and published. Nobody had tried to scroll that table with a keyboard on a phone-sized screen.

What I believe

A checklist is a promise you have to remember to keep. A test keeps it for you. That doesn't make the checklist useless. It makes it a draft: each line is a test waiting to be written, or a reminder that a person still has to look.

It's the same small-team habit I bring everywhere else. Find the check that keeps getting skipped, and make it cheap enough that it never does.

What I did

I built this with Claude, Anthropic's AI assistant. I asked for the checks, and Claude wrote the tests in Playwright and axe-core (both open source), chose many of the specific checks, and set up the workflow that runs them. My part was directing the work and deciding what to accept: what the tests covered, which failures were real, and which fixes went live.

Every test runs on every page at two widths, desktop (1440px) and phone (390px). Not every line on the list could become a test, so those stayed on the list.

Next, Claude checked the tests themselves. A test that can't fail isn't protecting anything, so it planted two bugs on the About page: a skipped heading level and an em dash. Both tests failed, the way they should. Then it put the page back, and they passed.

Last, Claude added a GitHub Actions workflow so the checks run on every push. If something fails, the report is saved with the run.

What it changed, and what I'd refine now

The table bug got fixed: both tables can now take keyboard focus, and each is labeled by its caption. One of the first failures was the test's fault, not the site's. A check on page descriptions was too strict, so Claude fixed the test. That's worth remembering: a red result is a question, not a verdict.

The checks now run in under a minute on every push, and GitHub Actions is free for public repositories.

The tests didn't catch everything. When I added my conference paper page, every test passed. But a screenshot Claude took at phone width showed a comparison table that hid its most important column off the edge of the screen. Nothing was technically broken. It just didn't work for the reader. We rebuilt it as cards.

That's the refinement I'd make next. Screenshot comparison would catch layout changes between versions. A screen reader pass is still manual, and it should stay on the list.

Take it with you

  • Turn your checklist into tests, one line at a time. Start with the line you skip most. Keep the lines a test can't judge on the list.
  • Prove each test can fail. Plant the bug it's meant to catch, watch it go red, then put things back.
  • Look anyway. Passing tests tell you nothing is broken. Only looking tells you it works for the person reading it.

Looking forward

Working with Claude made the code the fast part. That left my time for the part QA is for: deciding what done means, and making sure the checks mean something.

I'm hopeful about that trade. The tests and the reasoning behind them are public in my site's repository (opens in a new tab), so you can read them, run them, or borrow them.
